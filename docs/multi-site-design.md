# 多站点适配：设计

状态：**阶段 1 已实现**（X 用户主页、List）；**阶段 2 第一版（手动“判断本页”）已实现**（见第 8.3 节；真实 Chrome 端到端已跑，证据仍有明显缺口）；阶段 3 只是设计，未承诺，未实现。整体方向见 `anyfilter-vision.md`，远期条目见 `roadmap.md` 第 5 条。本文回答两件事：还要适配哪些页面，以及通用网页的内容怎么读到、怎么判断、怎么复核。

## 1. 三个阶段

| 阶段 | 范围 | 权限变化 | 状态 |
| --- | --- | --- | --- |
| 1 | X 用户主页（Posts 标签）、X List 时间线 | 无，仍然只有 `https://x.com/*` | 已实现 |
| 2 | 通用网页的**单篇文档**判定（如一篇博文），页面徽标，复用复核颜色约定 | 第一版实际只加了 `activeTab` 与 `scripting`，没有站点权限（见 8.3） | **第一版已实现**：手动、结果显示在侧栏；页面徽标、复核标注、自动模式、逐站授权未做 |
| 3 | 按站点的**信息流适配器**（Substack 首页与评论、HN、Reddit 等） | 同上，逐站 | 设计 |

### 1.1 阶段 1 实际做了什么

- 这两类页面和主页用同一套 `article[data-testid="tweet"]` 单元格，所以读取、隐藏、复核装饰都没改。唯一的差别是页面白名单，已经抽成 `src/domain/x-pages.ts`，不依赖 DOM，可以单测。
- 用户主页只放行 Posts 标签（`/<handle>`）。Replies、Media、Likes、关注者列表不放行：回复标签里的帖子没有父帖上下文，`replies` 范围的规则会退化；Media 和 Likes 不是普通帖子流。
- List 只放行 `/i/lists/<id>` 本身，不放行成员和关注者页。
- 验证样本采集（`capture.ts` 的 `xPageOf`）**刻意保持更窄**，仍然只有主页、搜索、帖子页。过滤和复核只读屏幕上已有的内容，不留存；采集会存帖子文本。主页和 List 上的帖子不会进入验证样本库，`PRIVACY.md` 里的采集说明因此不变。
- 已知的产品取舍：你专门打开一个人的主页，说明你想看他的帖子，过滤模式下仍可能把其中命中规则的帖子折叠。可以在侧栏里恢复，复核模式下只标注不隐藏。如果这在实际使用里让人不舒服，再考虑“主页不隐藏，只复核”的开关，现在不加。

## 2. 内容单元有三种形态

现在的代码只有一种单元：X 上的一条帖子。多站点要先分清：

| 形态 | 例子 | “过滤”的含义 |
| --- | --- | --- |
| 信息流 | X、Substack 首页或归档、HN、Reddit | 逐条判断，隐藏或标注，和现在一样 |
| 单篇文档 | 一篇博文（如 noahpinion 上的文章） | 整页一个判定，用页面徽标显示。**不隐藏正在读的文章**；最多提示“这页可能是 XX”，由用户决定 |
| 文档内的子项 | 评论区、嵌入的推文 | 属于信息流形态，需要按站点写适配器 |

一个提醒：好文章（如上面的例子）本来就不该被过滤，这类页面的价值是“值不值得读”的提示，和 `anyfilter-vision.md` 里“往上挑”的方向一致，不是“往下筛”。

## 3. 读取网页内容

### 3.1 选择：Defuddle

Obsidian Web Clipper 的做法（核对过 `src/content.ts`）：在内容脚本里对当前文档调用 `new Defuddle(document, { url })`，取回 `content / title / author / published / description / language / image / schemaOrgData` 等字段，解析前先展开 Shadow DOM，并给解析加了超时。Defuddle 是 MIT 协议，由同一作者维护，源码见 https://github.com/kepano/defuddle。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **Defuddle（选用）** | 宽松，保留正文的同时去掉导航、侧栏、评论等噪声；有元数据；有 X、Reddit、HN、GitHub 等站点抽取器可参考；`includeReplies` 可控制回复 | 依赖多一个包，需要测量打包体积 |
| Mozilla Readability | 老牌，稳定 | 偏严格，只面向文章，元数据少，一些页面直接返回空 |
| 自己取 `og:title`、`meta author`、`article` 或 `main` 的 `innerText` | 零依赖 | 对结构杂乱的页面很脆，提取质量会直接变成判定质量，最后还是要补 |

只用核心包取纯文本和元数据，**不引入 `defuddle/full`**（Markdown 转换我们用不上）。

### 3.2 提取结果

```ts
interface ExtractedDocument {
  url: string;            // 页面地址，去掉 query 与 fragment
  canonicalUrl: string;   // link[rel=canonical]，缺则等于 url
  title: string;
  author: string;
  site: string;
  published: string;
  description: string;
  language: string;
  text: string;           // 纯文本，已按字数上限截断
  wordCount: number;      // 截断前的字数
  truncated: boolean;
}
```

### 3.3 送给模型的内容

- 整篇文章一次发给模型比一条推文贵得多，所以要有硬上限。**取标题、摘要、小标题，加正文开头若干字**，上限数值要先在真实页面上测量，不预设。
- 被截断要在判定里如实标出（`truncated`），不能把“只看了开头”当成“看完了”。
- 页面上嵌入的内容（比如文章里引用的推文）当作作者放进正文的内容看待，不递归展开。
- 缓存键用规范化 URL 加正文内容哈希，和现在 `postContentKey` 的思路一致：正文变了，旧答案作废。

## 4. 权限与隐私

`roadmap.md` 已有的约束：**不把 X 的站点权限扩大成全站读取。**

- （自动模式才用；第一版未采用，见 8.3）`optional_host_permissions` 声明可选的全站权限，默认不授予。
- 侧栏里的“在这个站点启用”按钮调用 `chrome.permissions.request({ origins: [origin] })`，一次只授权一个站点，用户可随时在同一位置撤销。
- 授权后通过 `chrome.scripting.registerContentScripts` 动态注册该站点的内容脚本；未授权的站点扩展完全读不到。
- 阶段 2 的第一版**只做手动**：用户点“判断本页”才提取、才外发，不自动扫描。自动模式要另外定义打扰上限和费用上限，见 `roadmap.md` 第 2、3 条的做法。
- 实现前要验证两件事：侧栏点击能否拿到 `activeTab`（这决定第一版能不能连持久授权也不要）；`permissions.request` 从侧栏页调用是否满足用户手势要求。**已在探针上验证，结果见 4.1。**
- 首次在某站点外发前，明确告知：**这一页的文字会发给你选的模型服务商**。`PRIVACY.md` 要新增专门一节，列出发送的字段（标题、作者、摘要、截断后的正文、被问的规则）。
- 默认不处理登录后的私密页面：邮件、网盘、内网、网银等。要不要外发是逐来源的决定，见第 7 节。

### 4.1 平台行为验证结果

探针扩展和复现脚本在 `tmp/permission-probe/`（不入库；`README.md` 有完整结果表和手动清单，`results.json` 是原始结果）。环境：Chrome for Testing 153.0.8010.12，真实侧栏，CDP 可信鼠标事件；工具栏图标点击用 `Extensions.triggerAction` 代替。**自动化不等于真人点击。手动清单：2026-09-30 你在日常 Chrome 153.0.8010.53 上重做的第 1、2 步与下面的自动化结果完全一致（第 1 步 `executeScript` 失败且 `tab.url` 为 hidden；第 2 步图标点击后成功，换标签页失败、回来成功、跨源后失败）。第 3 步（授权确认框、持久授权、`tabs` 确认框文字）没有收到记录，下面 `permissions.request` 弹窗相关的部分仍是未验证。** 当天更早的一次记录里第 1 步曾出现 `executeScript` 成功，重做后没有复现，原因没有查清，最可能是那个标签页留有之前点图标的授权或残留模式；详见 `tmp/permission-probe/README.md`。

**问题 1：侧栏点击能拿到 `activeTab` 吗？——不能，但工具栏图标点击可以。**

| 情形 | 侧栏里 `executeScript` |
| --- | --- |
| 侧栏里的按钮点击（不论侧栏怎么打开） | 失败；`tab.url` 也读不到（`hidden`） |
| 用 `setPanelBehavior({ openPanelOnActionClick: true })` 让图标点击直接开侧栏 | **失败**。这个开法不带 `activeTab`；**现在的 `background.ts` 用的正是这个** |
| 用 `chrome.action.onClicked` 接图标点击，处理函数里同步 `sidePanel.open` | 成功；处理函数里立刻能读 `tab.url` 并 `executeScript` |
| 上一行之后，同一标签页里后续在侧栏点击 | 成功，授权留在该标签页上 |
| 换到另一个没点过图标的标签页 | 失败，需要再点一次图标 |
| 点过图标的标签页跨源导航 | 失败（授权收回） |

含义：

- “连持久授权也不要”**可行，但代价是每个标签页、每次跨源都要用户点一次工具栏图标**。第一版只做手动“判断本页”，用户本来就要点图标打开侧栏，这个代价可以接受；侧栏在别的标签页上要提示“请在该页点一下扩展图标”，不能显示一个点了会失败的按钮。
- 前提是把 `openPanelOnActionClick` 换成 `action.onClicked` + `sidePanel.open`。这会动到现有 X 侧栏的开启方式，实现时需要回归，并且要处理 `restrictPanelToX` 把非 X 标签页的侧栏设成 `enabled: false` 这一现状（本次没有验证 `sidePanel.open` 在被禁用的标签页上的表现）。
- 还有一个小坑：侧栏里读不到 `tab.url`，也就不知道“当前是哪个站点”。要么在 `action.onClicked` 里记下来（图标点击那一刻能读到），要么额外申请可选权限 `tabs`。探针里申请 `tabs` 返回了 true，之后任意标签页的 `tab.url` 都可读，但 `tabs` **不带**页面访问权（`executeScript` 仍失败）。这条权限在用户眼里写的是什么，要等手动清单第 3 步 6 的记录，别提前假设。

**问题 2：`permissions.request` 从侧栏调用满足用户手势吗？——满足，但有严格的时限和调用位置。**

| 调用方式 | 结果 |
| --- | --- |
| 侧栏点击处理函数里直接调 | 成功 |
| 同上，先 `await chrome.tabs.query` 再调 | 成功 |
| 点击后等 6.5 秒再调 | 失败：`This function must be called during a user gesture`（用户激活约 5 秒过期） |
| 侧栏 `sendMessage` 给 service worker，SW 收到后**第一句**就调 | 成功（手势能传到 SW） |
| 同上，SW 里先 `await` 任意异步再调 | 失败 |
| 没有点击，程序直接调 | 失败，立刻报手势错误 |

含义：“在这个站点启用”的按钮直接在侧栏页里调 `permissions.request` 最稳；不要绕 SW，更不要在中间夹存储读取、网络请求或 `setTimeout`。origin 要在点击**之前**就准备好（存在 state 里），不要点了以后才去查。

**自动化没能回答的：**

- 请求真实站点 origin 时，Chrome 的确认框是否一定出现。多次运行有时 pending（弹窗在等人）、有时直接返回 true 且 `getAll()` 里出现该 origin，原因没查清，大概率与自动化下的窗口焦点有关。**不能据此断言“授权不会弹窗”或“会弹窗”，等手动清单。**
- 授权之后 `registerContentScripts` 的实际表现（没有授权就无法在自动化里跑到这一步）。
- 真人点击图标是否与 `triggerAction` 完全等价。

**现状约束（已处理，2026-09-30）：** 原先 `background.ts` 用 `enablePanelForTab` 只在 x.com 启用侧栏，并在 `onInstalled` 里设 `openPanelOnActionClick: true`。第一版已换成 `action.onClicked` + `sidePanel.open`，侧栏对所有标签页可用，`openPanelOnActionClick` 每次启动置为 false。`optional_host_permissions` 第一版没有加（走 `activeTab`，不需要），留给自动模式。

## 5. 数据模型与适配器

### 5.1 数据模型：只加字段，不另起一套

`Post` 现在绑定了 X（`statusUrl`、`handle`、status ID）。复核、评估、缓存、面板都在用它，另起一套代价太大。建议只增不改：

- `source: 'x' | 'web'`，缺省为 `'x'`，旧数据不用迁移。
- `url`：规范链接。有它时 `postUrl` 直接返回它，否则退回现在的 `statusUrl`。
- `title`：文章标题，X 帖子为空。
- `kind` 增加 `'article'`。
- 文章的 `id` 用规范化 URL 的哈希。

`classifier.ts` 里的 `stateOf` 要区分：帖子送 `author/text/quoted/replyingTo`；文章送 `title/author/site/published/description/text`，并带 `truncated`。

### 5.2 适配器

```ts
interface SiteAdapter {
  id: string;
  /** 这个 URL 属于哪种形态，不认识就返回 null。 */
  surface(url: URL): 'feed' | 'document' | null;
  /** 信息流：就是现在的 TimelineView。 */
  feed?(): TimelineView;
  /** 单篇文档：读出文本，画页面徽标。 */
  document?(): DocumentView;
}
```

X 成为第一个适配器，行为不变。其余站点按 `surface()` 匹配，没有匹配的站点什么都不做。

## 6. 规则、成本、复核

- **规则要有适用范围。** 现有 10 条规则是按 X 短文本调的（见 `rule-tuning-2026-09.md`）。给规则加 `surfaces`，与现在的 `scope` 并列；内置规则保持只适用于 `post`。
- **文章的候选规则**（只是方向，规格要按 `filter-rules.md` 的格式先写清楚再实现）：标题党、纯营销、SEO 垃圾、低信息量复述、明显的机器批量生成内容。
- **预算。** 沿用现有的费用上限，并新增“单页字数上限”。
- **复核。** 页面徽标沿用 `anyfilter-vision.md` 的颜色约定，并且文字也要标出来（棕红、绿、琥珀、金色），不能只靠颜色。标注复用 `ReviewLabel`，身份用规范化 URL 加内容哈希。徽标在页面里用 Shadow DOM，不改页面自己的样式。
- **评估。** X 上的准确率数字**不能**搬到文章上。文章要有自己的样本、盲审和报告。文档样本默认只存摘录加 URL，不存整篇，版权和隐私都更稳妥。

## 7. 阶段 3：信息流适配器的进入条件

每加一个站点，先回答 `roadmap.md` 的四个问题，再写适配器：

1. 内容的身份怎么识别（稳定 ID 是什么）？
2. 能不能外发给模型？私密内容默认不外发。
3. 本地保存多久？
4. 用户怎么删除？

候选次序，按价值和风险粗排（不是承诺）：

| 站点 | 单元 | 备注 |
| --- | --- | --- |
| Substack 首页、归档、Notes、评论 | 卡片、评论 | 与阶段 2 的文档判定共用站点授权 |
| Hacker News | 条目、评论 | 结构简单稳定 |
| Reddit | 帖子、评论 | 不同界面版本的结构可能不同，进入时先逐一验证 |

不做自动识别“任意网页里的重复卡片”这种通用启发式：误判难以解释，也无法评估。

### 7.1 三个候选站点的评估

这一节只回答“要不要进、按什么顺序进、进之前要满足什么”，**不写适配器**。DOM 观察来自 `tmp/defuddle-spike/probe-feeds.mjs` 与 `probe-substack-dom.mjs`（不入库，原始输出 `out/feeds-probe.json`）：无登录态的全新浏览器，只读页面，不绕过拦截，每页只看了一次。观察日期 2026-09-29，选择器会随站点改版失效，所以写的是“这次看到了什么”，不是保证。

#### 四问（`roadmap.md` 第 5 条）

下面的答案是**建议口径**，不是已实现的行为。“本地保留”与“用户如何删除”都以现有实现为基线：过滤和复核只读屏幕上已有的内容、不留存；复核标注存身份加标签；验证样本采集只覆盖阶段 1 列出的 X 页面，新站点默认**不**进入采集。具体删除入口在实现时需要对照 `PRIVACY.md` 逐项核对，本次没有核对。

| 问题 | Substack | Hacker News | Reddit |
| --- | --- | --- | --- |
| 身份 ID | 文章：规范 URL 的 `/p/<slug>`（卡片上的链接）。评论：数字 ID，DOM 里是 `id="comment-<数字>"`，链接是 `/p/<slug>/comment/<数字>`。Notes 这次没有观察，不下结论 | 条目和评论共用 `tr.athing` 的 `id` 属性，即站点的数字 ID（观察到 `49890051`、`8863`、评论 `9224`）。最稳 | **这次没有拿到页面，无法回答。** 新版页面无登录态返回了近乎空白的页（约 143 字符），old.reddit.com 直接 403。已知的 `shreddit-post` / `thing` 属性等只是推测，见下 |
| 能否外发 | 公开文章的卡片与公开评论：与 X 帖子同一口径，经用户选定的模型服务商、首次告知。付费文的**预览**、订阅者专属内容：默认不外发，需要阶段 2 里提出的付费墙信号（`isAccessibleForFree=false` / `.paywall`）才能区分。Notes 待定 | 公开内容，与 X 同一口径。没有登录后私密内容（收藏、私信不在这两类页面上） | 公开帖子可以按同一口径；登录后的私有社区、私信、模组页默认不外发。但拿不到页面，能否稳定读取本身还是未知 |
| 本地保留 | 沿用现有：过滤不留存；复核标注存身份加标签（身份用什么、是否存正文，以 `ReviewLabel` 现状为准，本次没有逐项核对） | 同左，ID 用数字 ID | 同左（若进入） |
| 用户如何删除 | 复核标注与缓存沿用现有入口；站点授权在侧栏撤销（`permissions.remove`）。注意：**撤销授权不会自动删除已存的复核标注**，实现时要决定是否连带清理 | 同左 | 同左 |

四问里真正有阻碍的是 Reddit 的第一问。其他两个站点的“身份”都能从 DOM 直接读到，Reddit 需要先能稳定读到页面。

#### 排序建议与进入门槛

排序（只是意见，需要你确认）：

1. **Hacker News**：身份最稳、DOM 最简单、没有私密内容和授权分歧，作为**第一个适配器**验证“`SiteAdapter.feed()` 加逐站授权”这套机制最便宜。缺点是它的价值最低：条目是外链标题，评论文字短，这里“过滤”能给的帮助有限，主要价值是验证架构。
2. **Substack**：价值更高（评论区噪声、首页推荐），但有三件事要先定：付费墙信号、卡片文字的读取时机、`role="article"` 在不同页面含义不同。且它和阶段 2 共用站点授权，应在阶段 2 稳定后再做。
3. **Reddit**：暂缓。没有读到页面就没有评估基础。

统一的进入门槛（任何一个站点都要满足才开始写适配器）：

- 阶段 2 已实现并稳定（本表的前提，不是本次能决定的）。
- 该站点的四问在**实际读到的页面**上都有可验证的答案，且 PRIVACY.md 的新增段落已写好。
- 在真实页面上验证过选择器，并留下离线夹具，测试不依赖在线站点（沿用阶段 1 的离线夹具做法）。
- Reddit 额外要求：先确认无登录态或用户自己的浏览器里能稳定读到帖子列表；如果只能靠绕过拦截才行，就不做。

**本次没有做的：** 没有在用户已登录的浏览器里看这些站点；没有测 Substack Notes、`substack.com/home`、HN 的“更多”翻页、Reddit 任何页面；没有验证这些站点的服务条款是否允许扩展读取页面（`roadmap.md` 第 4 条对自动滚动提过同类要求，这里同理）。
